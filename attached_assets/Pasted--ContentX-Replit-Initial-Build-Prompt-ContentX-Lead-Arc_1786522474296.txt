# ContentX — Replit Initial Build Prompt

너는 ContentX 프로젝트의 Lead Architect이자 Senior Full-Stack Engineer다.

지금부터 Replit에서 새로운 프로젝트를 개발한다.

먼저 이 프로젝트의 목적과 아키텍처 원칙을 정확히 이해하고, 임의로 범위를 확장하지 마라.

==================================================
1. PRODUCT DEFINITION
==================================================

프로젝트명: ContentX

ContentX는 특정 플랫폼용 시나리오 생성기가 아니다.

ContentX의 목표는 다양한 콘텐츠를 구조화된 형태로 생성, 관리, 분해, 합성, 변환, 재사용, 공유할 수 있는

"Platform-Independent AI Content Engine"

을 만드는 것이다.

활용 대상:

- Movie
- Novel
- Screenplay
- Advertisement
- Roleplay
- Training
- Game
- Game Quest
- Board Game
- Simulation
- Business Use Case
- Worldbuilding
- Education
- Marketing
- Media

ContentX에서 생성되는 콘텐츠는 특정 플랫폼에 종속되지 않아야 한다.

RoleplayX는 ContentX를 사용하는 첫 번째 외부 플랫폼일 뿐이다.

따라서 다음 구조를 기본 원칙으로 한다.

Canonical Content
        ↓
Content Graph
        ↓
Content Engine
        ↓
Projection / Adapter
        ↓
External Platform


==================================================
2. ABSOLUTELY IMPORTANT ARCHITECTURE RULE
==================================================

현재 RoleplayX에서 사용하는 Scenario JSON을 ContentX의 Canonical Schema로 사용하지 마라.

RoleplayX JSON은 하나의 Projection Format이다.

예를 들어 RoleplayX의 다음 개념:

- context
- objectives
- successCriteria
- personas
- recommendedFlow

는 ContentX 내부의 Canonical Content에서 변환되어 생성되어야 한다.

즉:

ContentX Canonical Model
        ↓
RoleplayX Adapter
        ↓
RoleplayX Scenario JSON

구조로 구현한다.

향후 동일한 Canonical Content를 다음으로도 변환할 수 있어야 한다.

        ↓
Movie
        ↓
Novel
        ↓
Game
        ↓
Advertisement
        ↓
Board Game
        ↓
Training
        ↓
Use Case

- Location

- Event

- Dialogue
- Narrative
- Rule

모든 객체는 stable ID를 가져야 한다.

예:

entity_xxx
event_xxx
relationship_xxx
content_xxx

Array index를 ID로 사용하지 마라.

==================================================
8. CONTENT GRAPH
==================================================

ContentX의 핵심은 Content Graph다.

예:

Character
   │
   ├── works_for → Organization
   │
   ├── lives_in → Location
   │
   ├── wants → Goal
   │
   ├── conflicts_with → Character
   │
   └── participates_in → Event


Relationship은 단순 문자열이 아니라 독립적인 데이터 객체로 관리한다.

예:

{
  "id": "relationship_001",
  "source": "entity_001",
  "type": "conflicts_with",
  "target": "entity_002",
  "attributes": {
    "intensity": 0.8,
    "reason": "제품 출시 일정"
  }
}


중요한 관계를 description 안에만 저장하지 마라.


==================================================
9. DATABASE
==================================================

MVP에서는 PostgreSQL을 우선 사용한다.

가능하면:

PostgreSQL
+
JSONB
+
pgvector

구조를 사용한다.

처음부터 Neo4j 등의 별도 Graph Database를 도입하지 마라.

Content Graph는 PostgreSQL에서 먼저 구현한다.

필요한 경우 향후 Graph Projection을 별도로 추가할 수 있도록 Repository Layer를 만든다.


==================================================
10. VERSIONING
==================================================

Content는 수정될 때 이전 상태를 추적할 수 있어야 한다.

최소한:

- version
- createdAt
- updatedAt
- author
- parentVersion

을 고려한다.

향후:

- branch
- fork
- merge

를 지원할 수 있도록 설계한다.

기존 Content를 무조건 덮어쓰지 마라.


==================================================
11. PROVENANCE
==================================================

ContentX는 외부 콘텐츠를 모티브로 새로운 콘텐츠를 만들 수 있어야 한다.

따라서 provenance를 처음부터 설계한다.

예:

{
  "source": {
    "type": "url",
    "uri": "...",
    "title": "..."
  },
  "operation": "remix",
  "createdAt": "...",
  "generatedBy": {
    "provider": "...",
    "model": "..."
  }
}


향후 다음 작업을 추적할 수 있어야 한다.

External Source
      ↓
Extract
      ↓
Modify
      ↓
Remix
      ↓
New Content


외부 콘텐츠를 가져왔는데 출처 정보가 사라지는 구조를 만들지 마라.

==================================================
14. AI PROVIDER ABSTRACTION
==================================================

특정 LLM에 종속되지 않도록 한다.

예:

AIProvider
 ├── OpenAI
 ├── Gemini
 ├── Anthropic
 └── Local Model

현재 사용 가능한 API가 없더라도 개발이 중단되지 않도록 Mock Provider를 만든다.

API Key를 코드에 직접 작성하지 마라.

Replit Secrets / Environment Variables를 사용한다.
