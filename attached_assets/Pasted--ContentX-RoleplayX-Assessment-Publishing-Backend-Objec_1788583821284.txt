# ContentX → RoleplayX Assessment Publishing Backend

## Objective

Implement the ContentX outbound publishing pipeline for RoleplayX.

ContentX is the canonical authoring/compiler system.
RoleplayX is the runtime assessment system.

The existing RoleplayX import boundary is already implemented:

* POST `/api/content/import/validate`
* POST `/api/content/import`

and accepts `AssessmentScenarioPackageV1`.

Do NOT modify RoleplayX in this task.

The goal is to implement the ContentX side:

```text
ContentX Scenario(s)
    ↓
Assessment Package Compiler
    ↓
AssessmentScenarioPackageV1
    ↓
Validation
    ↓
Immutable Package Version
    ↓
RoleplayX Publish Client
```

---

# 3. Implement deterministic compiler

Create:

```ts
compileAssessmentScenarioPackage(...)
```

The compiler must be deterministic.

Do NOT call an LLM during compilation.

Source inputs may include:

* ContentX `DramaticScenario`
* scenario classification
* scenario lineage
* characters/personas
* competencies
* evaluation definitions
* simulation configuration

The compiler must produce a valid `AssessmentScenarioPackageV1`.

Mapping must be explicit and documented.

At minimum:

```text
DramaticScenario.title
    → package metadata title / scenario title

DramaticScenario.synopsis
    → scenario description/context.situation

DramaticScenario.stakes
    → context.stakes

DramaticScenario.acts
    → flow/stages and recommendedFlow

DramaticScenario.characters
    → personas

Scenario classification / competency metadata
    → competencies

Assessment evaluation configuration
    → evaluation dimensions

Assessment runtime configuration
    → termination/simulation/analytics
```

Do not invent unsupported facts.

When source data cannot populate a required RoleplayX field, return a structured compiler diagnostic instead of silently fabricating content.

# 7. Content hash

Before publishing:

1. Remove the supplied `provenance.contentHash`.
2. Canonicalize JSON recursively with sorted object keys.
3. Compute SHA-256.
4. Put the digest into `provenance.contentHash`.

The digest must represent the actual package sent to RoleplayX.

Do not trust externally supplied hashes.

# 8. Publish service

Create:

```ts
publishAssessmentVersion(...)
```

Flow:

```text
load package
↓
ensure version exists
↓
ensure version is immutable
↓
compile package
↓
validate package
↓
compute SHA-256
↓
POST RoleplayX /validate
↓
if valid:
    POST RoleplayX /import
↓
persist publish result
↓
mark package version published
```

Do not mark the ContentX package as published unless RoleplayX import succeeds.

---

# 9. Idempotency

Use a deterministic request key:

```text
contentx:{packageId}:{version}:roleplayx:{organizationId}:{categoryId}
```

Pass it as:

```http
Idempotency-Key: ...
```

If the same package/version/target is published again:

* do not create another ContentX publish record unnecessarily
* do not create duplicate RoleplayX content
* return the existing successful result where possible

RoleplayX already performs package-version conflict detection. Preserve that behavior.

# 13. Important architectural restrictions

DO NOT:

* modify the existing Content Graph schema to add RoleplayX fields
* make ContentX directly access the RoleplayX database
* copy the RoleplayX Scenario table into ContentX
* make RoleplayX depend on ContentX at runtime
* use an LLM during package compilation
* rewrite the existing JSON Format engine
* remove the existing generic export
* modify existing simulation runtime behavior
* create bidirectional synchronization yet

The architecture must remain:

```text
ContentX
  canonical authoring
       ↓
  assessment package
       ↓
  publish API
       ↓
RoleplayX
  runtime copy
```
