==================================================
1. PRODUCT VISION
==================================================

ContentX must NOT become merely:

- an AI content generator
- a CMS
- a prompt management system
- a roleplay scenario builder
- a collection of independent content tools

ContentX should become:

"An AI-native canonical content graph and world modeling platform that can represent people, characters, populations, worlds, relationships, events, goals, conflicts, behaviors and rules, then use AI agents to generate, simulate, transform, evaluate and project that canonical model into multiple content/runtime formats."

The core conceptual pipeline is:

Population
    ↓
Character / Entity
    ↓
Relationship / Dependency
    ↓
World / Context
    ↓
Agent
    ↓
Simulation
    ↓
Behavior / Event / Outcome
    ↓
Canonical Content Graph
    ↓
Projection

Possible projections:

- Roleplay
- Training
- Novel
- Movie
- Game
- Interactive fiction
- Marketing
- Education
- Simulation
- Future unknown formats

RoleplayX / RoleplayBot is a downstream projection/runtime.
It must NOT become the canonical domain model of ContentX.

4. FUNDAMENTAL DESIGN PRINCIPLE
==================================================

Separate these concepts strictly:

CANONICAL DATA
vs
RUNTIME STATE
vs
PROJECTION

For example:

Character
    ≠
Agent
    ≠
AgentState
    ≠
RoleplayScenario

A Character is a persistent canonical entity.

An Agent is a runtime actor instantiated from a Character.

AgentState is mutable runtime state.

A RoleplayScenario is a projection/task/runtime-specific representation.

Do not mix them.

10. DEPENDENCY GRAPH
==================================================

This is one of the most important new capabilities.

Introduce a dependency rule system.

There are TWO different kinds of graph relationships and they MUST NOT be confused.

A. Semantic Relationship Graph

Example:

Character A
    worksAt
Organization B

Character A
    reportsTo
Character C

Character A
    conflictsWith
Character D

B. Statistical / Generative Dependency Graph

Example:

occupation = manager
    →
authorityLevel = high

occupation = engineer
    →
technicalAffinity = high

ageBand = 45-54
    →
careerStage = senior

These must be represented separately.

Recommended domains:

SemanticRelationship
DependencyRule

Do not use one generic relationship type to represent both semantics and probability.
